## 1. 차세대 백오피스 / 고객포탈

> `2024.02 ~ 2025.07` · 약 1년 6개월 · 플랫폼서비스팀

**개요** — 그룹웨어 다우오피스 3.0 → 4.0 전면 개편에 따라 상품·할인·주문·계약·사이트·정산을 관리하는 백오피스(영업·운영 부서용)와 고객포탈(고객사가 직접 주문·결제·관리)을 신규 구축. 100명 이상 참여, 약 2만 고객사 대상

**역할** — 풀스택 개발(설계·개발·운영) — 상품·할인 관리 전담, 주문·계약/사이트 일부, 통합 알림·컨텐츠(광고) 서버 설계·개발

**기술** — `Spring Boot` `JPA` `Querydsl` `RabbitMQ` `Spring AOP` `Spring Cloud Gateway` `FeignClient` `HttpExchange` `GCS` `Kubernetes(GKE)` `Vue.js`

### ① 분석·설계
- 레거시 시스템과 차세대 요구사항을 바탕으로 상품·주문·할인·계약·사이트 등 백오피스 전 영역 도메인 분석, 도메인 경계 10개 이상·Aggregate 정의, ERD·아키텍처 설계
- 고객포탈/백오피스 시나리오·기획서 정합성 검토 — 시나리오 테스트로 요구사항 불일치 발견 → 관련 부서 재협의
- 결제 시스템 이관 구조 설계

### ② 상품·할인·주문
- 상품·할인 관리 개발 전담(전략 패턴)
- 백오피스/고객포탈 주문·계약·사이트 일부 개발, 중복 주문 및 결제 문제 해결

### ③ 야간 자동 카드 결제 배치의 트랜잭션 경계 정리
- 고객 1명 = 트랜잭션 1개로 분리, 실패한 고객만 롤백하고 다음 고객은 계속 처리

### ④ 메일/SMS 통합 알림 구조 재설계 및 42종 알림 개발
> 2025.04.28 ~ 06.21 · 커밋 257개 · 파일 173개 · PR 6건 · 설계·백엔드·배치·프론트 담당

| | |
|---|---|
| **문제** | 알림이 업무 트랜잭션 안에서 동기 실행 → 롤백된 처리의 알림 발송, 메일 서버 지연이 주문 응답으로 전파, 대량 발송 중단 시 이력 0건, 실패 원인 미기록, 도메인마다 발송 코드 복제(진입점 7곳·시그니처 5종) |
| **해결** | 커밋 이후(AFTER_COMMIT) 이벤트 + @Async의 독립 파이프라인으로 분리 / 이벤트에는 식별자만 싣고 커밋 후 재조회 / 메일·문자 전용 스레드풀로 수신자 단위 비동기 발송 / 수신자별 이력 상태 머신(대기 → 성공·실패+원인), 매시 정각 스케줄러로 묶음 상태 확정 / 데이터 생성기·채널 전략·발송 절차 템플릿·유형 enum 계약으로 책임 분리 |
| **효과** | 롤백 건 알림 0건, 메일 서버 장애가 주문으로 전파되지 않음, 수신자 단위 추적·재발송 근거 확보, 신규 알림은 **유형 선언 1개 + 생성기 1개 + 발행 1줄**로 추가(주문·사이트 코드 수정 없음) |
| **확인** | 기존 5가지 문제 상황을 테스트 API로 재현해 모두 해소됨을 검증 |

### ⑤ 컨텐츠(광고) 서버 분리

| | |
|---|---|
| **문제** | 백오피스(하위 메뉴 65개 이상)에 광고 로직 혼재, 10분마다 약 2만 고객사 전수 매칭 스케줄러, 고객포탈 외 포탈은 프론트 하드코딩 운영 |
| **해결** | 광고 도메인을 단독 컨텐츠 서버로 분리(백오피스는 인증·게이트웨이 역할) / 스케줄러 제거 → 주문·해지 시점에만 RabbitMQ로 최소 회사 정보 프로비저닝 / 게시 위치를 DB 테이블로 관리(상품·사용자 유형·포탈 위치별 게시, 상태·조회수 관리) |
| **효과** | 광고 반영 **최대 10분 → 즉시**, 전수 매칭 스케줄러 제거, 게시 위치 추가 = SQL 1회, 백오피스 장애에도 광고 노출 지속, 사업부 직접 운영 |

**세부 이슈**
1. **이벤트 발행 보장** — 주문 트랜잭션 안에서 이력(PENDING) 저장 → 커밋 후 fanout 발행 → 수신 서비스 성공/실패 회신 기록 → 전부 성공 시 마감 → 누락·실패 건은 관리 화면에서 같은 revisionId로 재발행(멱등). 4개 이벤트·12개 수신 서비스가 같은 구조 공유
2. **수신 처리 안정성** — 공통 흐름(이력 확인 → 처리 → 이력 저장 → 회신)을 커스텀 어노테이션 AOP로 분리, 성공 회신은 커밋 후에만, 실패 회신은 리스너 에러 핸들러가 사유와 함께 보장
3. **이미지(GCS) 보상 트랜잭션** — DB 롤백 시 AFTER_ROLLBACK 이벤트로 퍼블릭 버킷에 옮긴 이미지를 임시 버킷으로 원복
4. **서버 간 오류 메시지 전달** — 호출부 AOP로 HTTP 4xx/5xx 본문을 전용 예외로 변환, 글로벌 예외 핸들러가 원문 메시지 응답 → 프론트 수정 없이 운영자가 원인 확인
5. **배포 환경 전용 5xx** — 구간별 로그·응답 헤더 비교로 nginx 프록시 구간의 chunked 헤더/본문 불일치 원인 확정(Content-Length 부여 시 정상, 제거 시 503 재현) → 사내 스토리지 라이브러리에 반영 요청, 같은 원인의 엑셀 다운로드도 해결

### ⑥ 성과·공유
- 담당 기능 QC pass 100%
- 팀 동기들과 JPA·Hibernate 학습 후 1~2주마다 팀 공유

## 2. 임직원 복지몰 애드웰

> `2025.07 ~ 2026.07` · 약 1년 · 프로젝트수행팀

**개요** — 기업 임직원 대상 B2B 복지몰(쿠폰 + 배송 상품) 신사업. HR 담당자가 복지성 선물을 모바일 알림톡으로 대량 발송. 기존 쿠폰 서비스 코드를 복지몰 구조로 전환하고 배송(실물) 상품 적용

**역할** — 풀스택·운영 — 주문·전시·마케팅 기능 설계·개발, 운영, 인수인계

**기술** — `Spring Boot` `MyBatis` `MariaDB` `Redis` `Vue 3` `Pinia` `CoreUI` `외부 쇼핑몰 BO REST 연동`

### ① 주문 (주문 V2 정책 · 주문 화면 개편)
- **주문 타입별 정책** — 즉시/예약/기념일 발송, 다수 수신자, 일반형·선택형·즉시배송·페이포인트 주문 타입별 정책 구현·정리(발송 시각, 상태 전이, 취소 시한)
- **금액 계산** — 일반형(전 상품 합 × 수신자 수)·선택형(지정상품 1건 × 수신자 수), 배송상품 (판매가 + 옵션추가금) × 수량, 충전금 우선 차감 후 부족분만 PG(KCP) 결제, 최소 결제 1,000원 보정, 선택형 확정·차액 환급 산식
- **지정상품(대표상품) 자동 선정·동기화** — 프로모션 제외 우선, 실효 판매가 최고 1건, 추가·삭제·옵션 변경 시 재선정, 서버 검증(선택형은 지정상품 정확히 1개)
- **배송(실물) 상품 주문 적용** — 옵션 유형(단품·선택형·2/3조합형·텍스트형) 처리. 텍스트형은 같은 옵션번호라도 입력값이 다르면 별개 상품 → 진입 경로(장바구니=DB, 상품상세=화면 상태)와 무관하게 Pinia store로 수량·입력값을 운반하고, 옵션 단위 1줄 응답을 주문 줄 수만큼 확장하는 구조 설계
- 주문 화면 상품 추가(중복 검사: 쿠폰=상품번호, 배송=옵션번호+입력값), 상품 상태별(판매중단·상품품절·옵션품절) 노출 정책
- 수신자 엑셀 업로드·다중 행 붙여넣기, 알림톡 + 쿠폰 템플릿을 메시지 카드로 통합, 템플릿 미리보기·변수 파싱, 최근 템플릿 불러오기
- **결제 전 검증 흐름** — 중복 클릭 방지, 잔액·한도 재계산, 환금성·구매제한·옵션·발송시간·수신자 검사

### ② 전시·마케팅 공통 엔진
- 전시 관리 기능 5종 개발: 기획전(배송상품 추가), 큐레이션(신규), 레이어팝업(신규), 뱃지 관리(신규), 배송상품 가격 노출 관리(신규)

| | |
|---|---|
| **문제** | 기능마다 전용 테이블·서비스·검증 로직 복제 (기능 N개 = 코드 N벌 = 정책 N곳) |
| **해결** | ContentType 기반 공통 등록/수정/삭제/전시여부/순서 엔진 + 타입별 Validator 구현체로 정책 분리. 타입·정책이 고정된 엔진을 타입별 빈으로 등록해 주입(분기문 제거, 싱글톤에 타입을 런타임 교체할 때의 동시성 문제 회피). 공통 테이블 공유 + 타입별 확장 테이블 |
| **효과** | 큐레이션·레이어팝업을 공통 엔진 위에서 구현, 새 전시 기능은 타입·Validator 정의만으로 추가, 정책이 한곳에 모여 담당자가 바뀌어도 규칙 확인 가능 |

### ③ 동시성
- 전시 순서 변경 시 `SELECT … FOR UPDATE`로 '채널 + 타입' 구간 선점
- 인덱스 컬럼 순서(채널, 타입, 순서)를 락 조건과 일치시켜 **넥스트키 락 범위 한정** → 다른 채널·타입 작업은 대기 없이 처리
- 데드락 재시도 AOP (150ms 후 새 트랜잭션, 최대 3회)

### ④ 캐시
- 전시 목록 Redis **시간대별 키(TTL 1시간)** 설계 — 노출 기간이 '시' 단위인 점에 착안, 정각이 지나면 키가 바뀌어 자동 전환
- 전시 시작·종료용 배치·스케줄러 0개, 홈 진입마다 돌던 조회를 채널·타입별 시간당 1회 수준으로 감소, 전시 중 항목 변경 시 해당 키만 evict해 즉시 반영

### ⑤ 연동
- 외부 쇼핑몰 BO와 카테고리·브랜드·상품·주문·배송·클레임 REST API 연동

### ⑥ 어드민 대시보드
- 사용자·매출·전시 현황

### ⑦ 운영·문서

## 3. 애드콘 배송 실물상품 도입 · 반응형 전환

> `2026.08 ~ 현재` · 2026.11 오픈 예정 · 프로젝트수행팀

**개요** — 모바일 쿠폰·상품권 구매·선물·대량 발송 B2C/B2B 서비스에 배송(실물) 상품을 도입하고, PC/모바일로 나뉜 화면을 반응형으로 전환. 운영 중인 JSP 레거시의 기존 정책은 유지하면서 구조 확장

**역할** — 풀스택·선행 개발 — 분석·설계 → 개발 → 검수 대응 → 운영 인수인계

**기술** — `JSP` `jQuery` `Spring Boot` `MyBatis` `MariaDB` `REST API`

### ① 분석·설계 (선행 개발)
- 기존 ERD(107개 테이블·1,042개 컬럼) 분석, 배송상품 적용을 위한 데이터 구조 재설계
- 기존 Controller 구조의 REST API 전환 설계·적용: JSP form용 Controller와 REST용 ApiController 이원화, sqlSession 직접 호출 → Mapper 인터페이스 전환, 팀 개발 가이드 초안 수립

### ② 전시 관리 (어드민·서비스)
- 테마·기획전·답례·특가 이벤트에서 쿠폰/배송상품을 함께 판매하도록 전시·상품 구조 확장
- 테마·기획전·답례 3개 상품관리 화면을 공용 구조 하나로 통합(화면·core 공통, 검증 정책·API 호출만 화면별 도메인 JS로 주입)
- 쿠폰/배송 카테고리 통합(배송 카테고리 4뎁스 트리, 노드 단위 조회, 재귀 CTE), 어드민 카테고리관리

### ③ 메인·상품목록
- 메인(특가·인기·신상)에 배송상품 가격 노출·뱃지 적용, 인기상품 배치 개선
- 전체상품보기 반응형 개편 + 배송상품 샵 신규: 좌측 필터(카테고리·가격·브랜드) 실시간 검색, 정렬 4종, 브랜드 전용관 개편
- 쿠폰/배송이 파라미터만 다른 동일 REST API를 쓰도록 검색·카테고리 API 통합
- 비로그인 가격 마스킹을 화면이 아닌 서버 응답에서 처리

### ④ 검색

### ⑨ 조회 성능 개선 2건

#### 주문내역 '배송 상품' 탭 조회 지연 해결 `2026.11.04 ~ 11.05`

**문제** — "가끔, 처음만 느린"(2.6~3.3초) 원인 미상 지연. 재조회는 30ms라 재현이 어려웠음

**원인** — 쿠폰·배송 원장을 UNION ALL로 합친 뷰를 조인할 때 DB가 뷰 전체(메시지 수십만 행)를 임시 테이블로 물리화(SQL 3개 × 약 1초). DB 쿼리 캐시가 재조회만 빠르게 만들어 문제를 가림. 합성 데이터 50만 건으로 재현하고 EXPLAIN/ANALYZE로 확인

**해결** — 조건·집계·계산식은 그대로 두고 "이 회원·이 기간의 주문"으로 읽는 범위를 먼저 좁히는 CTE + 조인 순서 고정으로 물리 테이블을 인덱스로 읽게 함(매퍼 XML 1개 수정). 매퍼 전체를 바꾸는 초기 설계안은 영향 범위가 커 보류하고 최소 변경으로 재설계

**검증** — 배포 전 15개 조건의 응답 JSON 저장(해시로 결정성 확인) → 배포 후 주문 단위 전 필드 대조(변경 0 · 누락 0, 증가분 검산)

| 항목 (검수 서버 실측) | Before | After | 개선 |
|---|---|---|---|
| 새 조건 첫 조회 | 3,164 ~ 3,285ms | 144 ~ 210ms | **약 16배** |
| 콜드 3건 동시 호출 | 각 6,250ms | 181 ~ 274ms | **약 25배** |
| 목록 SQL | 1,212ms | 228ms | 약 5배 |
| 쿼리 캐시 의존 | 있음 | 제거 | |

#### 검색바 추천 구매이력 쿼리 최적화 `2026.11.11 ~ 11.12`

**발단** — 취소한 주문의 브랜드가 추천 1순위로 노출되는 버그를 수정한 PR에 자동 코드 리뷰가 "전체 메시지 스캔" 지적

**해결** — 회원의 주문번호 → 그 주문의 메시지 → 주문별 상태 집계 순으로 범위를 좁히는 CTE(읽는 순서 고정). 테이블명만 바꾼 1차 시도는 실행계획으로 효과 없음을 확인하고 기각

**측정 설계** — 비로그인은 해당 쿼리를 호출하지 않는 점을 이용, 로그인/비로그인 응답 시간 차이로 쿼리 1개의 비용을 분리 측정
